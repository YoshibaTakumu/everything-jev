# 時間の見積もりと実績

drain の手順 1〜2 で開始前の見積もりを作り、波の区切りと前提が変わった時に更新する。見積もるのは依頼から所定の終了条件までの**経過時間**。エージェントの延べ稼働時間、トークン量、料金は別の指標であり、時間から換算しない。

## 範囲と終了条件を固定する

- 対象の親・末端 Issue、取得時刻、基点 revision、経路・モデル・本体と委譲先の同時実行数を記録する。現在のフロンティアだけか、merge で解放される後続も含む drain かを区別する。
- 「実装済み」「検証済み」「レビュー済み」「merge と Issue close 済み」を分ける。入力待ちを残して終了する時刻と、全件完了する時刻を同一視しない。
- 同じ子を複数の親から重複計上しない。親が集約だけなら子に加えて実装工数を足さず、親固有の受け入れ条件があれば別の工程にする。
- 別の本体が担当中の作業は引き取らず、進捗が観測できれば残りを条件付きで扱う。取得が欠ける・循環がある・終了条件が決まらない範囲に、有限の完了時刻を約束しない。

## 完了条件から工程を起こす

各 Issue の残作業を次に分け、実装済みなら実装を重ねて見積もらない。共有の準備は一度だけ数える。

| 工程 | 見積もる対象 |
|---|---|
| 調査・準備 | 未決の照合、旧版との比較、契約、隔離ツリー、依存とデータの準備 |
| 実装・取り込み | 既存実装例の有無、変更する層と共有ファイル、本体が行う統合 |
| 検証 | 変更対象に必要な検査、build、実行環境の準備、成果物の確認 |
| レビュー・修正 | 対象差分の規模と領域、必須観点、最も遅い観点、集約、採用修正、変更後の再検証 |
| 統合・終了 | PR、ローカル検証と必須 CI、逐次 merge、main 追従と再検証、Issue 照合、片付け |

「検証だけ」の場合も、データの所在・接続・版一致・復元可能性が確認済みかを調べる。保存 schema があることは稼働 DB との一致を保証しない。到達の確認は許可された読み取り範囲で行い、所要時間を測るためだけに重い build や本番操作を実行しない。

各工程に短め・通常・長めの時間と根拠を添える。根拠は、同じモデル・経路・近い変更規模の実績を優先し、無ければ仮置きと書く。検査は cache、ホスト、CPU アーキテクチャ、データ量が違えば同じ速さとはしない。このリポジトリで観測した実績が無ければ未計測とし、別の環境の所要時間を標準時間として持ち込まない。

未確認のデータの版・実行基盤・メモリ・CI 利用可否・大きなレビュー差分など、長めのシナリオを生む条件を名指しする。仕様や入力の到着時刻が不明なら、その待ち時間は「未定」。都合のよい分数や一律の余裕率で隠さず、「入力到着後に残り○〜○分」のように条件付きで提示する。開始前の調査で時間が掛かる場合は、判明した工程と未確認項目を先に報告し、調査自体の経過時間も残す。

## 依存と実行資源から経過時間を求める

Issue の native な依存に加え、同じファイル・本体の取り込み作業・同じ DB・build のメモリなど、同時に実行できない工程を並べる。これは見積もり用の順序であり、Issue の辺を書き換えることではない。

各工程の開始は「前提工程の終了」と「担当・実行資源が空く時刻」の遅い方、終了は開始に所要時間を足したものとする。短め・通常・長めのシナリオでこの計算を行い、最後の必須工程の終了を求める。完了を支配する工程列をクリティカルパスとして示す。

- 独立した並列作業は重なる区間を一度だけ数える。本体が順番に取り込むなら、取り込みまで並列としない。
- 複数観点の並列レビューは各レビュー時間の合計ではなく、最も遅い観点までの時間と集約・修正で決まる。同時実行枠が足りなければ待ち列を入れる。人数で全体を割らない。
- レビュー待ちに録画できるなら重ね、レビュー修正で録画や build の前提が変わる場合は再実行を追加する。同じ余裕を工程と全体の両方に足さない。
- wave ごとの単純合計は、後続の先行作業を重ねられない場合に限る。merge が必要な依存と、契約上許される先行作業を分ける。

例: 20 分と 30 分の独立した実装、その両方に依存する本体の統合 10 分なら、経過は 40 分。実装が同じファイルを変えるなら 60 分。これは計算の例であり、この repository の標準時間ではない。

## 開始前に提示するもの

```markdown
対象・終了条件: <親と末端の範囲、現在の波／範囲全体、merge まで等>
観測: <時刻、revision、経路・モデル、実行枠、環境>
現在の波: 通常 <分>、想定範囲 <短め〜長めの分>
範囲全体: 通常 <分>、想定範囲 <短め〜長めの分>、または未定の理由
完了を支配する工程: <依存する工程列>
不確実性: <未確認事項、長めになる条件、入力・判断待ち>
根拠と確かさ: <実績の参照、条件の差、件数、仮置き箇所>
次の更新: <最初の波の終了、版照合の結果など>

| 工程・Issue | 前提・実行資源 | 短め／通常／長め（分） | 根拠 |
|---|---|---|---|
```

範囲はシナリオによる予測であり、確率区間ではない。実績の件数と条件を示せない P50/P80 や「±10% の精度」は付けない。実装の依頼が既にある場合、見積もり提示のために再承認を求めない。予算・期限が指定されていて収まらない場合だけ、完了できる波と残りの扱いを提示する。期限は未完了の検査を省略する理由にしない。

## 実績を残して補正する

記録は gitignored な `local/` など引き継ぎ可能な作業用の保存先に置き、初期見積もりを更新値で上書きしない。製品コード・恒久仕様へ実行ログを混ぜず、秘密・実データ・ログ全文は保存しない。終了時に記録の所在を返す。一時保存で消える場合はその限界を明記し、利用者から保存を頼まれたら保持できる場所へ移す。

開始前の表とともに、工程の開始・終了・保留・再開時に次を記録する。毎ツール呼び出しを記録し直す必要はない。

| 波・Issue・工程・試行 | 担当・実行資源 | 開始／終了（時差付き） | 状態・根拠 | 予定との差の理由 |
|---|---|---|---|---|

根拠は対象 revision、検査結果・PR・実行記録への参照。工程は重なってよい。実測・進捗報告の時刻で区切った概算・未観測を区別する。コマンドの duration 合計や繰り返した状態取得から経過時間を作らず、実行 ID で重複を除き、時刻区間の重なりを考慮する。

終了時は初期見積もりとの差を、範囲変更・環境の復旧・追加実装・検証の再実行・レビューの再読・人間待ちに分けて説明する。複数原因の区間が重なるときは足し合わせない。待ち中も別作業が進んだ時間を、全体から丸ごと引かない。進行中の記録には観測時点と下限だけを残し、完了実績の平均へ混ぜない。

波の終了、新しい blocker、通常の見積もりを超える見通し、レビューや検証の想定回数の超過で、残りの工程から見積もり直す。報告は [monitoring-frontier](../../monitoring-frontier/SKILL.md) にまとめる。再読が続くレビューは、確認済み・未確認・未解決点の増減から進行を調整する。時間切れをレビュー完了としない。

次回は近い条件の完了実績と照合し、当初の予測範囲に実績が入ったかも残す。外れの理由を補正し、異なる規模・未完了の実行を単一の「Issue 当たり分数」に均さない。
