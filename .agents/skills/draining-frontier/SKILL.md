本体が対象範囲と完了条件を統制し、利用可能な実行環境で作業を進める。1 周を**波**と呼ぶ。波は「再取得 → 仕分け → 実装 → 検証 → PR → 許可された merge」で、merge が次のフロンティアを解放する。

グラフの取得と分類は [sequencing-issues](../sequencing-issues/SKILL.md)、変化と保留の報告は [monitoring-frontier](../monitoring-frontier/SKILL.md) を使う。開始前に [時間の見積もりと実績](references/ESTIMATION.md) を読む。

## 範囲と権限

対象の repository・親 Issue・終了条件を既存の依頼から確定する。親が複数なら子孫の和集合を取り、repository と番号で重複を除く。親をまたぐ blocker とファイル競合も範囲全体で扱う。別の担当が進めている Issue は、その担当と作業範囲を照合する。

見積もりだけの依頼では、読み取りと見積もりの提示で終える。実装も依頼されていれば、見積もり提示のために再承認を求めず、既存の権限内で進める。依存の辺の変更、外部への投稿、merge は依頼で許可された範囲に限る。実装依頼だけから release PR の merge、パッケージ公開、有料サービスの利用、本番書き込みへ権限を広げない。

merge が依頼に含まれない場合は、PR と検証結果を用意したところで止める。人間が決める仕様や入力が必要な Issue だけを**保留**にし、独立した作業は進める。

## 手順

1. **実行環境と範囲の未決を確認する。** 指定された実行環境があれば、その利用可否と権限を確認する。到達できなければ、既に許可された代替を使うか、必要な選択を尋ねる。対象の全 Issue の本文と完了条件を読み、仕様判断・入力待ちをまとめる。回答済みの問いは繰り返さない。
   - 完了: 対象範囲、実行環境、終了条件、未決の一覧が分かる。
2. **再取得して仕分ける。** sequencing-issues で現在のグラフを取り直す。フロンティアを **着手**・**決定待ち**・**入力待ち**に分ける。グラフ上の分類と実行上の保留は別に持つ。同じファイルを変える Issue は直列にする。
   - 初回は現在の波と範囲全体の見積もりを提示して保存する。後続の波では実績との差と残り時間を更新する。
   - 完了: フロンティア全件の扱いが決まり、人間待ちの解消条件が記録されている。
3. **実装する。** 最新の基準 branch を取得し、Issue ごとに隔離した branch または worktree で作業する。既存の命名規約に従い、他の担当の変更を上書きしない。
   - 並列実行が利用可能で依頼の権限内なら、独立した作業を委譲する。各契約に Issue、基点 SHA、担当ファイル、完了条件、検査、外部変更の範囲を明記する。本体と委譲先で同じファイルを同時に編集しない。
   - 委譲先からは変更・検査結果・未解決点・成果の所在を受け取り、本体で統合を確認する。委譲できなければ本体が順に実装する。
   - 完了: 各 Issue の差分が完了条件に対応し、未決があれば保留へ移っている。
4. **検証する。** 変更対象の [AGENTS.md](../../../AGENTS.md) と適用されるルールを読み、実装後は [CONTRIBUTING.md](../../../CONTRIBUTING.md) の検査を実行する。委譲先の成功報告だけで統合後の検証を代えない。UI など追加の検証が必要な変更は、その検証も行う。
   - 完了: 実行した検査は成功し、未実行の検査と制約が明示されている。
5. **PR を準備する。** commit・push が許可されていれば、Issue ごとに draft PR を作り、完了する Issue を `Closes #番号` で結ぶ。リポジトリのレビュー要件に従って指摘を解消し、検証後に ready にする。
   - PR の差分はその Issue の完了条件に閉じる。依存先の作業を先行させる場合は別 branch・別 PR にし、親 PR の merge 後に base と検査を更新する。
   - 完了: 対象 SHA の検証結果とレビュー結果が揃い、未解決の判断は保留として分かる。merge の権限がなければここで報告する。
6. **許可された PR を1つずつ merge する。** 最新 head の必須チェックとレビューが満たされていることを確認する。1つ merge するごとに、残る PR の基点・衝突・検査を見直す。CI が未実行・実行不能なら、その事実とローカル検証結果を分けて報告し、必須チェックの回避や保護設定の緩和を行わない。
   - 完了: merge した PR と対応 Issue の close をそれぞれ確認できる。未解決の PR は保留にし、手順2へ戻る。
7. **終了と残余を報告する。** 着手できる作業がなくなったら、merge 済み PR、closed Issue、未mergeの成果、保留と解消条件、残る blocker を報告する。見積もりと実績の差を記録し、この作業で作った不要な worktree・branch は、成果の保存を確かめてから片付ける。
   - 完了: 完了と保留を区別でき、未完了の再開条件と成果の所在が分かる。

## 波をまたいで持つもの

- 保留・見積もり・実績は作業用の記録に残す。グラフは毎波再取得し、過去の観測を現在の着手判断に使わない。
- 初回、波の終了、新しい判断待ち・検証失敗・実行不能が生じた時に monitoring-frontier で報告する。同じ時点の観測を共有し、報告だけのために重複取得しない。
- 委譲先が同じ契約から繰り返し外れる場合は、原因を確認して本体で引き取るか保留にする。待機中は、独立した本体の作業や次の波の準備を進める。
- 検証の失敗と待ち状態を区別し、環境の問題は一時設定で切り分ける。利用者の永続設定を無断で変更せず、止まった Issue と無関係な作業は続ける。
