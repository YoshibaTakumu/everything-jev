# 苦手な構造と現行モデルの制約

確認日: **2026-09-22**。モデルごとの既知の制約と、アプリケーション側で検証する事項を分ける。

## Jev 1.13 で公式が挙げる弱点

以下は [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13) の要約。将来の版にも同じ弱点があるとは決め付けない。

| 苦手な構造 | 分け方・代替 |
| --- | --- |
| 暗黙の意図や例外を読み取らせる問い | 条件と候補の境界を明示する |
| 件数・金額・数値の精密な計算 | 計算はコードへ。意味による該当判定だけを聞く |
| 日時の前後・期間の比較 | 日付要素を抽出し、組み立て・比較・タイムゾーン処理はコードへ |
| 二重否定や何段もの間接参照 | 対象のフィールドと質問を直接対応させる |
| 無関係な情報が多い長い state | 先に検索・絞り込みを行う |
| 答えを誘導する敵対的な入力 | 境界例を評価し、実行をアプリケーションで制御する |
| instructions と criteria の矛盾 | 意味と yes/no の向きを揃える |
| 別質問間に数式上の恒等関係を期待する | 判断の定義を固定し、必要な整合性はコードで検証する |
| 自由文・コード・説明の生成 | 生成モデルへ分担する。既知候補からの選択なら Choice を検討する |

特に `Noul(A)` と別に聞いた `Noul(not A)` の和が必ず1になる、Noul と yes/no Choice の確率が一致する、といった仮定は置かない。Score の補間値から正確な数量を逆算することも避ける。

## 構造を変えれば使える場合

- 長い処理全体を Jev に解かせるのではなく、各段の意味判断だけに分解できれば適用の余地がある。
- 候補が多い分類では、候補を検索で絞る、階層を辿る、曖昧な分岐を複数保持するといった設計を評価する。
- 「見つからない」と「最も近い」を区別するため、候補外の経路や情報充足の確認を用意する。

これらは設計上の推奨。具体例は [ARCHITECTURE.md](ARCHITECTURE.md) と、[階層分類](https://docs.typesafe.ai/cookbooks/hierarchical_classification)、[候補値の抽出](https://docs.typesafe.ai/cookbooks/pre_parsed_value_extraction_cookbook) を参照する。

## モデル・入力・料金の確認表

**この表は確認日時点の値。利用前に [Models](https://docs.typesafe.ai/models) と [API](https://docs.typesafe.ai/api) を再確認する。**

| 項目 | 確認時点の公式記載 |
| --- | --- |
| バージョンID | `jev-1.13.0` |
| エイリアス | `jev-latest`・`jev-preview` はどちらも上記を指す。将来変更される |
| 入力 | テキストを含む文字列・JSON。画像・音声・動画を直接入力する方式は未対応 |
| コンテキスト | state と全質問の合計64kトークン以内。state と最長の1質問の合計32k以内 |
| Choice 候補 | 最大255 |
| Score 段階 | 2〜10 |
| 料金 | 入力100万トークン当たり $0.042、出力トークンは無料 |
| レート | 250,000 tokens/s、1,200 requests/min と記載。動的に変わる旨の注意あり |

英語を主な学習言語としており、日本語を含む他言語を同じ精度とみなさない。顧客ごとの fine-tuning / LoRA ではなく、state・質問・基準で用途を表現するのが現在の方式。[Models](https://docs.typesafe.ai/models)。

SDK が受け付ける型とHTTP仕様の説明が異なる場合は、利用版のSDKとAPIを照合する。本ガイドのサンプルは文字列・オブジェクトと明示した質問を使い、曖昧な型の許容に依存しない。

## アプリケーションが別途持つ責務

以下は本リポジトリの設計上の境界。

- 型付き応答でも、未知キー・欠損・不正値・分布を実行側で検証する。モデルが返す高い確信度を、権限・事実の証明・実行成功の証拠にしない。
- 永続メモリ、検索、ツール実行、監査、冪等性、改訂確認はアプリケーションが用意する。
- 入力中の命令をモデルだけで無害化できると期待しない。データアクセスや書き込み先をコードで制限する。
- 公式の cookbook は、その例のデータ・測定条件での結果。自分の用途では別の評価を行う。

参照: [security](../../../../docs/security.md)、[evaluation](../../../../docs/evaluation.md)。

顧客入力を学習に使わないという説明と、保存されないという保証は別。保存期間や契約条件は [Legal](https://docs.typesafe.ai/legal) の現行文書を確認する。ZDR は全利用者の既定とは説明されていない。
